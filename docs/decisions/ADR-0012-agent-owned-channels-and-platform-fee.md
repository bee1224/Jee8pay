# ADR-0012 — 高級代理自有渠道、資金歸屬與平臺費應收

Status: Accepted
Date: 2026-10-03

> 2026-10-09 使用者核可第一階段並確認三點：上帝看商戶一律從團長點進去（不保留全站商戶列表選單）；渠道金鑰由上帝輸入並派發；既有商戶歸到「平台直屬」。第一階段已實作（渠道帳號、派發、平台直屬、選單），payment 下單流程未變；第二階段起仍須逐階段回報後才動工。
> 用語：2026-10-09 起，畫面上的超級管理員、高級代理、一般代理分別改稱上帝、團長、隊長；本文沿用當時的寫法。
> 同日稍早的版本假設「上游帳戶由平台擁有、渠道成本由平台負擔」，經使用者澄清後不成立，已整份改寫。

## Context

平台的定位是「整合系統」，出租給高級代理使用。使用者在 2026-10-03 確認的經營方式：

- **承租的高級代理**：自己去找第三方支付渠道、自己找商戶。渠道費是他自己的成本，由他設定；向商戶收多少由他自己談定後輸入。平台只收承租前談好的平臺費（百分比），只有超級管理員能設定。
- **平台直屬高級代理**：超級管理員自己經營的一支，舊有的黑貓 PAY 五個上游與既有商戶歸在它底下。平臺費為 0、高代費為 0，唯一成本是渠道費，其餘利潤全歸這一支。
- **資金**：買家繳的錢進入高級代理自己的渠道帳號，不經過平台。平台只做整合與記錄。
- **平臺費**：訂單經過平台時記錄並預留，也就是系統逐筆累計每位高級代理應付的平臺費。
- **金鑰**：高級代理把第三方支付的金鑰交給超級管理員，由超級管理員輸入、建立渠道帳號並派發給該高級代理。串接程式只由平台開發。
- **不互撞**：每位高級代理只能使用派發給他的渠道帳號。一個帳號預設只屬於一位高級代理，經超級管理員明確操作後才可共用。
- 推薦佣金已移除（ADR-0009、ADR-0010 的修訂註記）。

現況與上述不符之處（code evidence）：

- 金鑰存在 `t_pay_interface_config`，唯一鍵為 `(info_type=3 商戶應用, info_id=appId, if_code)`；`ConfigContextQueryService.queryNormalMchParams` 只依 appId 取參數。沒有「渠道帳號」可以派發，也沒有地方記錄帳號屬於哪位高級代理。
- ADR-0010 的錢包假設平台持有全部資金：`SettlementSplit` 把商戶手續費減各層後的剩餘記入平台錢包，提現一律由平台撥款（`WithdrawService.markPaid` 只有平台端點；2026-10-03 新增的代理提現審核，同意只是註記）。
- ADR-0009 的平臺費與渠道費是全站預設（`t_fee_rule` 的 `DEFAULT`），只有平台能設；高代費另外設定。
- 代理新增商戶後仍須平台替該商戶應用填金鑰並建立 `t_mch_pay_passage`。

限制：ADR-0002（Provider 走 native extension contract，五個黑貓 PAY provider 不合併）；TD-001（`if_params` 尚無欄位層級加密，不應讓明文金鑰份數變多）；下單、回呼、結算屬核心流程，修改必須最小並先在隔離環境驗證。

## Decision

### 1. 渠道帳號

新增 `t_channel_account`：`account_id`、`if_code`、`account_name`、`owner_sr_agent_no`（帳號所屬的高級代理）、`shareable`（預設 0）、`state`、`remark`。

- 金鑰沿用 `t_pay_interface_config`，新增 `info_type=4`（渠道帳號），`info_id=account_id`。一個帳號只有一份金鑰。
- 只有超級管理員能建立帳號、輸入與修改金鑰。高級代理只看得到帳號名稱、支付方式與狀態，看不到金鑰。
- 「接口」仍是 ADR-0002 的 `ifCode` 與其 adapter，只有平台能新增。高級代理要用尚未串接的第三方支付時，須先由平台開發。同一家第三方支付的第二個帳號只要新增一筆渠道帳號，不必再複製 provider 程式。

### 2. 派發與不互撞

新增 `t_channel_account_agent(account_id, sr_agent_no)`：

- 預設只有擁有者一列。`shareable=1` 之後，超級管理員才能把帳號加派給其他高級代理。
- `t_mch_pay_passage` 增加 `account_id`。商戶只能使用「自己那一支的高級代理」被派發的帳號；綁定時與下單時各檢查一次，派發被撤銷就拒絕下單（fail closed）。
- 回呼依訂單找到通道與帳號，再由 provider adapter 驗證簽章與帳號身分；對不上就拒絕（AGENTS.md 的 callback ownership 不變）。

### 3. 取參數（唯一需要動 payment shared core 的地方）

`ConfigContextQueryService` 取 `NormalMchParams` 時：通道帶有 `account_id` 就依帳號取（`info_type=4`），否則照舊依商戶應用取。既有設定搬遷完成前照常運作。屬 YELLOW 修改；既有 extension point 不足的理由是唯一鍵把金鑰綁在商戶應用上，無法表達歸屬、派發與共用。

### 4. 手續費：誰設定、歸誰

| 項目 | 誰設定 | 歸誰 |
| --- | --- | --- |
| 商戶手續費 M | 高級代理（對旗下商戶） | — |
| 平臺費 P | 只有超級管理員，逐位高級代理設定（百分比＋固定金額） | 平台 |
| 渠道費 C | 高級代理，逐個渠道帳號設定 | 高級代理付給第三方支付的成本 |
| 代理費 A | 高級代理，對旗下一般代理設定 | 一般代理 |
| 高級代理利潤 | 不用設定：M − P − C − A | 高級代理 |

- 儲存費率時檢查 M ≥ P ＋ C ＋ A，不成立就拒絕。
- 平台直屬：P = 0，利潤 = M − C − A，歸平台直屬這一支（也就是平台）。
- 與 ADR-0009 的差異：平臺費由全站預設改為逐位高級代理；渠道費改由高級代理設定並記在渠道帳號上；高代費不再單獨設定，改為扣除各項後的剩餘。
- 下單時仍把當下的 M、P、C、A 快照到訂單；事後改費率不影響已成立的訂單。
- 可見範圍：超級管理員看得到全部；高級代理看得到自己這一支的全部；一般代理只看得到自己的代理費與自己商戶的費率。

### 5. 資金歸屬：以高級代理為單位

資金在高級代理自己的渠道帳號裡，平台不持有承租代理的資金。因此：

- 錢包（ADR-0010）改為「這一支內部的帳」：商戶與一般代理的餘額，代表高級代理應付給他們的金額。
- 提現由該支的高級代理審核並撥款（填匯款單號結案）。平台只對平台直屬這一支撥款，對其他支只能查看。
- 高級代理自己的利潤不設提現；系統提供報表。
- 凍結、解凍、黑名單維持以高級代理為範圍。

### 6. 平臺費應收

結算每筆訂單時，把該筆的平臺費記入「應收平臺費」帳（逐位高級代理一本）：

- 超級管理員可查每位高級代理的累計應收、已收與未收，並登記收款（日期、金額、備註）。
- 高級代理在後台看得到自己應付與已付的平臺費，方便他預留。
- 系統只記錄，不代為扣款；實際收款在系統外進行。是否要改成預存扣抵，另行決定。

### 7. 開戶流程

1. 超級管理員建立高級代理，設定他的平臺費。
2. 高級代理提供第三方支付金鑰；超級管理員建立渠道帳號、輸入金鑰並派發給他。
3. 高級代理設定該帳號的渠道費，新增旗下代理與商戶，替商戶勾選要用的帳號並輸入商戶費率。商戶即可收款，不需要平台再介入。

### 8. 平台直屬高級代理

建立一位高級代理「平台直屬」（`is_house=1`）：既有商戶歸到它底下；既有商戶應用上的金鑰轉成五個渠道帳號並派發給它；平臺費設為 0。由超級管理員以平台身分管理，利潤記入平台錢包。

### 9. 新增第三方支付接口的標準步驟

在 `docs/providers/` 補一份不綁定特定 provider 的 checklist（目錄與必要類別、金鑰只經 `if_params` 存取、獨立 exception、測試矩陣、provider README）。

### 分階段

| 階段 | 範圍 | 風險 |
| --- | --- | --- |
| 1 | 渠道帳號資料表與平台端管理畫面；平台直屬高級代理；把既有金鑰轉成渠道帳號並派發。payment 不變 | 低 |
| 2 | payment 依帳號取參數；綁定與下單時檢查派發 | 中，動核心流程 |
| 3 | 費率模型：逐位高級代理的平臺費、逐帳號的渠道費、利潤為剩餘；快照與結算拆帳；既有規則搬遷 | 高，動到錢 |
| 4 | 資金歸屬：提現改由高級代理撥款；應收平臺費帳與收款登記 | 高，動到錢 |
| 5 | 代理自己開戶（勾選帳號、輸入商戶費率） | 中 |
| 6 | 新增接口 checklist 文件 | 低 |

每階段在隔離環境驗證、部署到測試環境並回報後，才進行下一階段。

## Alternatives

**A. 金鑰仍放在商戶應用上，派發時複製到每個商戶應用。** 不必改 payment，但同一把金鑰會有多份明文副本（加重 TD-001），輪替要逐一同步，共用與撤銷只能靠比對副本。未採用。

**B. 沿用 JeePay 的服務商（ISV）模式。** ADR-0009 已決定代理是獨立實體；黑貓 PAY provider 只實作 `NormalMchParams`，改走 ISV 模式需重寫五個 provider。未採用。

**C. 讓高級代理自己在後台輸入金鑰。** 使用者選擇由超級管理員輸入，以掌握哪些帳號接進平台。未採用。

**D. 平臺費改為預存扣抵（餘額不足即停止收款）。** 收款有保障，但需要預存、扣抵與停用機制。使用者目前只要求記錄並預留，列為後續選項。

## Not in scope

- 金鑰欄位層級加密（TD-001）。
- 代付、多幣別。
- 合併五個黑貓 PAY provider 的實作（ADR-0002、ADR-0008）。
- 平臺費的自動扣款或預存機制。
- 正式環境的搬遷時程；本決策先在測試環境落地。

## Consequences

- 高級代理之間的渠道隔離由資料模型保證，並在下單時再檢查一次。
- 平台不持有承租代理的資金，法律與營運責任的界線較清楚；相對地，平臺費是系統外收款，可能有欠款，系統只提供應收紀錄。
- 手續費引擎、結算拆帳與提現撥款權責都要改寫（第 3、4 階段），是本決策最大的風險，各自單獨驗證。
- payment 的取參數流程多一個分支，屬 shared core 修改，需保持最小並補測試。
- 營運平台的費率畫面、代理後台的費率頁、提現審核與分潤報表都要跟著改；2026-10-03 部署的「代理同意只是註記」會被第 4 階段取代。

## Supersedes

通過後取代 ADR-0009 的「平臺費、渠道費為全站預設，高代費另外設定」與 ADR-0010 的「平台持有全部資金、剩餘歸平台、提現一律由平台撥款」；兩份 ADR 的其餘內容不變。
